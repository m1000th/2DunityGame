Qué hacen los dos ajustes de Git

No es trivia: si uno de los dos está mal, el proyecto se rompe para todo el equipo y no os enteráis hasta la semana 3.

  • Asset Serialization = Force Text. Guarda las escenas y prefabs como texto en vez de binario. Git solo entiende texto: si son binarios, lo único que puede deciros es «este archivo cambió», sin mostrar qué. Ojo: esto no hace que las escenas se puedan fusionar sin riesgo — el YAML de Unity está lleno de IDs internos y una fusión automática suele producir una escena corrupta. Hace los conflictos visibles, no inofensivos. Por eso la regla de una escena, una persona sigue en pie.
  • Version Control = Visible Meta Files. Cada archivo de Assets/ tiene un .meta al lado con un GUID único y sus ajustes de importación. Unity referencia los assets por GUID, no por ruta. Si alguien sube un .png sin su .meta, Unity le genera uno nuevo con otro GUID en el ordenador de al lado, y todas las referencias de todas las escenas se rompen: sprites en blanco y Missing (Mono Script) por todo el Inspector.

De ahí salen dos reglas prácticas: los .meta siempre se suben, y renombrar o mover assets se hace siempre desde dentro de Unity, nunca desde el Explorador de Windows — que mueve el archivo y deja el .meta atrás.

Trampa clásica

Los archivos .meta parecen basura y no lo son: conectan cada sprite y cada script con las escenas. Siempre se suben al repositorio. Si alguien no los sube, a los demás se les rompen todas las referencias.

01

Semana 1 — Que el personaje salte bien

Sin arte. Cubos blancos y ya está

Toda la semana sobre un nivel gris y feo, hasta que moverse y saltar sea agradable. Si el salto se siente mal aquí, se sentirá mal en los cuatro niveles y ya no habrá tiempo de arreglarlo.

Lunes y martes: aprender lo mínimo

Los cuatro hacéis el microjuego de plataformas de Unity Learn (learn.unity.com, gratuito y guiado). Dos días, no más. Con eso entendéis los cinco conceptos que necesita este proyecto: GameObject, Transform, Rigidbody2D, script y prefab. El resto se aprende sobre la marcha.

De miércoles a viernes: el jugador

  1. Capas de física En Project Settings › Tags and Layers cread Player, Ground, Enemy y Hazard. Todo lo demás depende de esto.
  2. El jugador Sprite Renderer + CapsuleCollider2D (la cápsula no se engancha en las esquinas) + Rigidbody2D con Gravity Scale: 3, Collision Detection: Continuous, Interpolate: Interpolate y Freeze Rotation Z marcado, o el personaje rodará por el suelo.
  3. Un hijo llamado GroundCheck Un objeto vacío justo a los pies. Desde ahí se detecta el suelo.
  4. Pegad el script de abajo Y ajustad los números en el Inspector hasta que os guste cómo se siente.
  5. El nivel gris GameObject › 2D Object › Tilemap. Al Tilemap: Tilemap Collider 2D + Composite Collider 2D + Rigidbody2D en Static, y marcad Used By Composite. Ponedlo en la capa Ground.
  6. Cámara Instalad Cinemachine desde el Package Manager, añadid una cámara 2D y arrastrad el jugador a Follow. Cinco minutos y queda mejor que un script propio.
  7. La primera build, el viernes Aunque solo haya un cubo saltando. Instrucciones en la semana 4 — leedlas ya.

El script incluye las dos cosas que separan un plataformas agradable de uno que frustra: coyote time (puedes saltar una décima de segundo después de salir del borde) y jump buffer (si pulsas salto justo antes de aterrizar, se guarda). Son seis líneas y valen su peso en oro.

// Assets/_Project/Scripts/PlayerController2D.cs
using UnityEngine;

[RequireComponent(typeof(Rigidbody2D))]
public class PlayerController2D : MonoBehaviour
{
    [Header("Movimiento")]
    [SerializeField] private float moveSpeed = 8f;
    [SerializeField] private float jumpForce = 16f;

    [Header("Detección de suelo")]
    [SerializeField] private Transform groundCheck;
    [SerializeField] private float checkRadius = 0.18f;
    [SerializeField] private LayerMask groundLayer;

    [Header("Sensación de salto")]
    [SerializeField] private float coyoteTime = 0.10f;
    [SerializeField] private float jumpBuffer = 0.10f;

    private Rigidbody2D rb;
    private float horizontal, coyoteCounter, bufferCounter;

    private void Awake() => rb = GetComponent<Rigidbody2D>();

    private void Update()
    {
        horizontal = Input.GetAxisRaw("Horizontal");

        bool grounded = Physics2D.OverlapCircle(groundCheck.position, checkRadius, groundLayer);
        coyoteCounter = grounded ? coyoteTime : coyoteCounter - Time.deltaTime;

        if (Input.GetButtonDown("Jump")) bufferCounter = jumpBuffer;
        else bufferCounter -= Time.deltaTime;

        if (bufferCounter > 0f && coyoteCounter > 0f)
        {
            rb.linearVelocity = new Vector2(rb.linearVelocity.x, jumpForce);
            bufferCounter = 0f;
            coyoteCounter = 0f;
        }

        // soltar el botón antes corta el salto: altura variable
        if (Input.GetButtonUp("Jump") && rb.linearVelocity.y > 0f)
            rb.linearVelocity = new Vector2(rb.linearVelocity.x, rb.linearVelocity.y * 0.5f);

        if (horizontal != 0f)
            transform.localScale = new Vector3(Mathf.Sign(horizontal), 1f, 1f);
    }

    private void FixedUpdate()
    {
        rb.linearVelocity = new Vector2(horizontal * moveSpeed, rb.linearVelocity.y);
    }

    private void OnDrawGizmosSelected()
    {
        if (groundCheck == null) return;
        Gizmos.color = Color.green;
        Gizmos.DrawWireSphere(groundCheck.position, checkRadius);
    }
}
Tres errores que vais a tener

Excepción al darle a Play, en la línea de Input.GetAxisRaw: falta poner Active Input Handling en Both (paso 4 del día 1) y reiniciar Unity. Vuestro proyecto viene con el Input System nuevo solamente, y ese ajuste es lo que permite usar también el código sencillo de este script.

El personaje se engancha al correr: os falta el Composite Collider 2D en el tilemap. Es el bug número uno de los plataformas con tiles.

Error en linearVelocity: en Unity 6 la propiedad se llama así; en versiones anteriores es velocity. Si copiáis código de un tutorial antiguo, es casi siempre esto.

Semana 3 — Los cuatro niveles

Cortos. De 1 a 2 minutos cada uno

Un nivel no es «un espacio con plataformas»: es una lección. Cada uno presenta una idea en un sitio seguro, la practica y la examina. Con esto los cuatro niveles se diseñan casi solos.

NivelEnseñaDiseñoDura
1 — IngresoCorrer y saltarCasi imposible morir. Huecos anchos. Sin enemigos hasta el final, y ahí uno solo, en terreno plano.1 min
2 — VistaPinchosEl primer pincho se ve desde arriba antes de tener que saltarlo. Saltos encadenados. Un checkpoint a mitad.1–2 min
3 — DeliberaciónEnemigos en serioEnemigos sobre plataformas estrechas, combinados con pinchos. Más verticalidad.2 min
4 — VeredictoNada nuevoExamen de todo lo anterior, más rápido y apretado. Un tramo final memorable. Checkpoints generosos.2 min

Repartíos los niveles: persona 3 hace el 1 y el 2, persona 2 hace el 3 y el 4. En paralelo, no en fila. La persona 3 pasa después el arte de Kenney por encima de los cuatro.

  1. Diez minutos de boceto en papel Antes de tocar el tilemap. Marcad dónde va cada checkpoint y cada enemigo. Ahorra dos horas de trabajo por nivel.
  2. Montadlo en gris primero Jugadlo, corregidlo, y solo entonces poned el arte. Cambiar el tilemap ya decorado cuesta el triple.
  3. Que lo juegue alguien de fuera Sin explicarle nada. Si muere tres veces en el mismo sitio, el problema es el nivel, no el jugador.
  4. Sprites de píxeles: ajustes de importación En el Inspector de cada sprite: Filter Mode = Point (no filter), Compression = None, Pixels Per Unit = 32. Sin esto salen borrosos.
Trampa clásica

Diseñar la dificultad según lo bien que jugáis vosotros. Habéis probado ese salto cien veces; quien os evalúe lo ve por primera vez. Todo debería ser bastante más fácil de lo que os parece.

04

Semana 4 — Pulir y generar el .exe

Lunes y martes: pulido · Miércoles: build · Jueves: arreglar · Viernes: entregar

Pulido — solo estas cuatro cosas

  • Sonido para todo. Salto, muerte, enemigo aplastado, botón del menú, meta. Es lo más barato de la lista y lo que más cambia la impresión: un juego con sonido parece el doble de terminado que uno mudo.
  • Música. Una pista para el menú y una para los niveles, en bucle.
  • Fundido a negro entre escenas. Quita el parpadeo brusco al cambiar de nivel.
  • Partículas al morir. Un pequeño estallido cuando muere el jugador o el enemigo.

Si sobra tiempo: sacudida corta de cámara al morir, y escalar levemente al jugador al aterrizar. Nada más.

Generar el .exe

  1. Añadid TODAS las escenas En File › Build Profiles (o Build Settings), abrid cada escena y pulsad Add Open Scenes. 00_MainMenu tiene que quedar en el índice 0. Una escena que no esté en esa lista no existe en el .exe, aunque funcione en el editor.
  2. Player Settings Company Name = nombre del equipo. Product Name = Verdict Zero (esto da nombre al ejecutable). Poned el icono en Default Icon.
  3. Ventana Fullscreen Mode = Fullscreen Window, resolución por defecto 1920×1080.
  4. Plataforma Windows, x86_64. En Scripting Backend dejad Mono: compila en minutos en vez de en media hora.
  5. Cero errores rojos en la consola Los avisos amarillos se pueden dejar.
  6. Build en una carpeta nueva y vacía Builds/VerdictZero_v1/, fuera de la carpeta Assets. Tarda entre 2 y 20 minutos. No canceléis.

Lo que sale no es un archivo suelto, es una carpeta:

VerdictZero_v1/ ├── Verdict Zero.exe ├── Verdict Zero_Data/ TODO el juego está aquí dentro ├── UnityPlayer.dll └── MonoBleedingEdge/
El fallo de entrega más frecuente

Enviar solo el .exe. Sin la carpeta _Data al lado no arranca: da error y se cierra. Se comprime la carpeta entera en un ZIP y se envía eso.

El aviso de Windows es normal

SmartScreen dirá «Windows protegió su PC» porque el ejecutable no está firmado. Se pulsa Más información › Ejecutar de todas formas. Ponedlo en el LEEME.txt para que nadie piense que es un virus.

Cinco reglas

Pegadlas en el chat del grupo hoy
  1. Una escena, una persona Se avisa antes de abrirla y al terminar de subirla. Las escenas y prefabs no se fusionan: el trabajo de alguien se pierde entero.
  2. Descargar antes de empezar, subir al terminar Cada sesión, aunque esté a medias. Un cambio pequeño y frecuente vale más que uno gigante el domingo.
  3. Todo lo que se repite es un prefab Si un enemigo está en tres niveles y no es prefab, arreglar un fallo son tres trabajos.
  4. Los números van en el Inspector Usad [SerializeField]. Así quien diseña niveles ajusta la velocidad sin abrir un script.
  5. Quince minutos cada día, no una reunión larga a la semana Tres preguntas: qué hice, qué haré, en qué estoy atascado. Con cuatro semanas, nadie puede estar atascado más de un día en silencio.

Si vais con retraso

Recortad en este orden exacto

Vais a ir con retraso — es normal. Lo que decide la nota es qué recortáis. Id quitando de arriba abajo:

  1. Acortad los niveles Cuatro niveles de 45 segundos siguen siendo cuatro niveles. Es el recorte que menos se nota.
  2. Quitad el enemigo, dejad los pinchos Un plataformas de obstáculos fijos funciona perfectamente y os ahorra el sistema entero de enemigos.
  3. Que los cuatro niveles compartan un solo tileset Sin variación visual entre niveles. Cambia la forma, no el decorado.
  4. Animación única Solo el sprite quieto, sin animar. Feo, pero se entrega.
Lo que nunca se recorta

La semana 4. Un juego pequeño y terminado se entrega; uno grande y roto, no. Si el miércoles de la semana 4 no hay un .exe probado en otro ordenador, no importa lo bueno que sea el juego en vuestro editor.
